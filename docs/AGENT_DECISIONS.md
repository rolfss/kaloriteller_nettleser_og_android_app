# Agent decision log

## AD-001 — Application stack
**Status:** accepted
**Date:** 2026-08-12

**Question:** Which concrete stack should implement the shared offline web and Android application?

**Decision:** Use React with strict TypeScript and Vite, Dexie over IndexedDB, Vitest/Testing Library, `vite-plugin-pwa`, jsPDF, and Capacitor.

**Why:** This matches the preferred stack, keeps one web codebase, and uses mature libraries only at persistence, PDF, PWA, and native platform boundaries.

**Alternatives considered:** Vanilla web components; a native Android UI; a larger state-management framework.

**User-visible effect:** The same sparse interface and local dataset work in Chrome/PWA and the Android wrapper.

**Reversibility:** Moderate; domain/application modules remain framework-independent enough to migrate.

## AD-002 — Navigation and application state
**Status:** accepted
**Date:** 2026-08-12

**Question:** How should a small four-view application navigate and keep UI state synchronized?

**Decision:** Use explicit view state in the application shell and reload persistent snapshots after mutations, without a router or global state library.

**Why:** The dataset and navigation hierarchy are tiny. IndexedDB remains canonical, while explicit refreshes avoid stale derived totals and unnecessary dependencies.

**Alternatives considered:** React Router; Redux/Zustand; optimistic cache layers.

**User-visible effect:** Simple in-app transitions between current day, history, day detail, and definitions.

**Reversibility:** Easy; URL routing can be added later without changing domain or persistence.

## AD-003 — Numeric presentation
**Status:** accepted
**Date:** 2026-08-12

**Question:** How should fractional calorie results be displayed while preserving precision?

**Decision:** Keep JavaScript numeric precision in snapshots and totals, and display calories rounded to the nearest whole kcal using Norwegian number formatting.

**Why:** This follows the domain recommendation and keeps ordinary logging readable without altering stored values.

**Alternatives considered:** Always show decimals; round each entry before summing.

**User-visible effect:** Compact whole-kcal values; totals are calculated from unrounded entry values before presentation.

**Reversibility:** Easy; presentation formatting is isolated.

## AD-004 — Android export
**Status:** accepted
**Date:** 2026-08-12

**Question:** How should Android export PDFs without broad storage permission?

**Decision:** Write generated bytes to the app cache through Capacitor Filesystem only after an export action, then open the native share sheet and remove the temporary file when practical.

**Why:** This is user-initiated, works with scoped application storage, and avoids startup or broad media/storage permissions.

**Alternatives considered:** Direct public-storage writes; a custom native document-provider plugin.

**User-visible effect:** Android presents the normal native save/share destinations during export.

**Reversibility:** Easy; the platform adapter is isolated.

## AD-005 — Explicit custom reinterpretation
**Status:** accepted
**Date:** 2026-08-12

**Question:** What should happen when a syntactically measured pending entry is explicitly changed to `Custom enhet` in the definition dialog?

**Decision:** Treat the editable item text as the new custom label, retain the original raw entry for history, and calculate the pending quantity with the explicitly supplied custom rate. Future custom use is entered as `<quantity> <custom label>`.

**Why:** No density or unit conversion is implied, and the user's basis change is explicit. The snapshot remains traceable to the created custom definition.

**Alternatives considered:** Disable basis changes; use the combined measure-and-item text as a custom label.

**User-visible effect:** A user can deliberately reinterpret the pending quantity as a count unit, but the app never auto-converts gram/deciliter values.

**Reversibility:** Easy; conversion logic is confined to pending-entry resolution.

## AD-006 — In-app completion confirmation
**Status:** accepted
**Date:** 2026-08-12

**Question:** Should explicit day completion use a browser-native confirm prompt or the app's accessible modal system?

**Decision:** Use a focused app modal with explicit cancel and completion actions.

**Why:** Production browser testing exposed inconsistent control of the native prompt. The app modal provides consistent focus handling, copy, touch targets, and behavior across PWA and Android.

**Alternatives considered:** `window.confirm`; a second inline button state.

**User-visible effect:** Completion is clearly explained and can be cancelled before any data changes.

**Reversibility:** Easy; the state transition remains in the same application service.

## AD-007 — Permission-free Android package
**Status:** accepted
**Date:** 2026-08-12

**Question:** Does the packaged Android app require the default network permission or broad file access?

**Decision:** Remove the default Android `INTERNET` permission and add no storage permission. Export uses the app-private cache and native share URI.

**Why:** All normal data and web assets are local, and Capacitor's local origin does not require a production network connection. This makes privacy enforceable at the package boundary.

**Alternatives considered:** Keep Capacitor's default network permission for possible future use; request public-storage access.

**User-visible effect:** The Android app cannot transmit food data over the network and only opens a save/share destination after an explicit export action.

**Reversibility:** Easy if a future, explicitly approved network feature changes the product constraints.

## AD-008 — Recruiter-facing repository and live demo
**Status:** accepted
**Date:** 2026-08-13

**Question:** How should the completed project be made immediately understandable and usable from GitHub?

**Decision:** Move the application from its redundant nested directory to the repository root, make the README a concise technical case study, and publish every verified `main` build to GitHub Pages.

**Why:** A root-level project structure is conventional and discoverable. A quality-gated live demo lets a reviewer evaluate the product without installing a toolchain while keeping the source, tests, and deployment evidence together.

**Alternatives considered:** Keep the nested specification package; provide local run instructions only; deploy to an unrelated hosting provider.

**User-visible effect:** The GitHub landing page now leads with a live demo, product screenshot, capabilities, architecture, verification status, and direct technical links.

**Reversibility:** Easy; hosting is static and the deployment workflow can be removed without changing the application.

## AD-009 — Browser-memory fallback
**Status:** accepted
**Date:** 2026-08-13

**Question:** How should the live demo behave on managed computers where persistent browser storage is disabled?

**Decision:** Try the normal versioned IndexedDB database first. If it cannot be opened, leave it untouched and automatically start an equivalent in-memory database for the current page session. Show the active storage mode in the interface.

**Why:** Recruiters can evaluate every core flow without installing the PWA, downloading files, or receiving permission to create custom project files. The warning prevents users from assuming temporary data will survive closing the tab.

**Alternatives considered:** Stop the app with an error; require private browsing; replace persistent storage for every user with session-only React state.

**User-visible effect:** Normal browsers retain data locally. Restricted browsers remain fully usable until the page reloads or closes and clearly explain that the data is temporary.

**Reversibility:** Easy; runtime storage selection is isolated from the domain and application service.

## AD-010 — Explicit recruiter demo
**Status:** accepted
**Date:** 2026-08-13

**Decision:** `?demo=1` bypasses persistent storage completely and creates a fresh in-memory database for each page load. The regular URL retains the existing persistent-first behavior.

**Why:** A recruiter can evaluate the real product without installing it, writing project files, reading prior app data, or leaving evaluation data behind.

**User-visible effect:** The demo is clearly labeled and resets on reload/close. A restart action is also available under Data and privacy.

## AD-011 — Portable data boundary
**Status:** accepted
**Date:** 2026-08-13

**Decision:** JSON backup is schema-versioned and validated as a complete replacement before a single transaction clears and restores the database. CSV cells are quoted and formula-like text is neutralized.

**Why:** Learned definitions are valuable local data. A strict replacement boundary is easier to reason about than partial merge semantics and avoids silent duplicates or alias conflicts.

**User-visible effect:** Users can back up or move their local state, export spreadsheet-friendly history, and explicitly clear all local data.

## AD-012 — Recoverable deletion and explicit retention loss
**Status:** accepted
**Date:** 2026-08-13

**Decision:** Entry and definition deletion offer a ten-second in-memory undo. Completing a day when seven completed days already exist names the oldest day and exposes history export before confirmation.

**Why:** These operations are locally destructive. Short-lived undo is fast for ordinary mistakes; retention loss must be visible before it occurs.

**User-visible effect:** Accidental deletion can be reversed immediately, while the fixed seven-day rule remains unchanged and transparent.

## AD-013 — Android recruiter artifact
**Status:** accepted
**Date:** 2026-08-13

**Decision:** Tags matching `v*` run a Java 21 Android build in GitHub Actions and attach a debug-signed APK to a prerelease explicitly labeled as a test package.

**Why:** It provides an installable evaluation artifact without presenting a debug key as production signing or requiring the local workstation to have an Android SDK.

**User-visible effect:** Recruiters may install a tagged test APK after accepting Android's external-source prompt. It is not represented as a Play Store release.
